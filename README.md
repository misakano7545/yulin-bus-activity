# 玉林实时公交

玉林（车来了城市码 440）实时公交面板。后端 Go 代理上游接口，前端是单页面板：
线路列表 → 线路详情（走向条 + 站点卡 + 车辆跟随 + 车辆列表）。

车来了没覆盖的县市线路走第二条数据面（掌上公交），目前接的是 **北流105路**，见文末一节。

只用标准库，没有第三方 Go 依赖。

## 使用提醒

照本项目的实时公交去坐车，请注意两点：

- **定位可能不准**：玉林公交的调度一体机等车载设备是 2018 年前后装的，车上报的位置
  和站序有偏差。显示「还有 N 个站」时，车可能已经更近或更远，别把它当成精确到分钟的准点表。
- **车辆是响应式停靠**：玉林市公共汽车公司的营运车辆均执行响应式停靠 —— 站台上没人
  招手示意、车上没人按铃，就不停。

所以个人建议：车距你所在的站还有 **1–2 站**时就做好上车准备，车进站前**招手示意司机**
停车上下客，别等车到跟前才起身。

## 跑起来

```sh
go build -o yba ./cmd/server
./yba -addr 127.0.0.1:8099 -plate-map plate_map.json
```

`-addr` 默认 `:8080`。`plate_map.json` 是车牌号（`licence`）到公交公司自编号的映射，
缺了不致命：非纯数字的车牌原样透出并记日志，跑一轮就能收齐待补项。

线上那台走 systemd（`yulin-bus-activity.service`，跑的是仓库里预先编好的 `yba`，经 cloudflared
挂在 `bus.haxwoi.eu.org`）。**改完代码要重新编译再重启，否则网页还是旧的一份**：

```sh
go build -o yba ./cmd/server && systemctl restart yulin-bus-activity
```

面板资源（`index.html`/`app.js`）是 `go:embed` 打进二进制的，所以前端改动同样得走这一步 ——
只改 `internal/panel/` 下的文件不会生效。

## 版面：窄屏单列，桌面端三栏

窄屏（<900px）还是原来那套：线路列表 ↔ 线路详情两页互斥，底栏放收藏/刷新/换向，走向条横排
（`.rail{width:max-content}` —— 只写 `min-width` 的话 `display:flex` 是块级盒，轴线会跟着铺满
容器、伸到末站之外）。

桌面端（≥900px）分三栏：左栏 284px 线路导航，右栏内容区再分「站点轴 1fr（≤920px）| 详情
440px」。配套几处：

- `#vList` / `#vDetail` 的 `hidden` 在桌面端被 `display:flex !important` 放开 —— 窄屏那套
  两页互斥是靠 `hidden` 切的，桌面端两页同时在场上，所以要在样式里盖掉。
- 底栏那三个动作 JS 里挪进顶栏右侧（`layoutActs()`，跟着 `matchMedia` 变），窄屏再挪回去。
  按钮是同一批元素，监听器不用重绑。
- 没选线路时桌面端默认打开第一条（`onHash` 里那一支）—— 左栏常驻，右栏不能空着。
- **走向条在桌面端转竖排**：一站一行（行高 `--ch`）、站名横排、绿线改竖轴（`.rail::before`
  换成 `left` + `top/bottom` 收半行）。横排 30 站要横向滚 292px，站名竖着写最长 9 行 135px
  —— 桌面端竖向空间多得多，换成竖列表后一屏十几站、鼠标滚轮直接滚。
- 内容区 `.body` 自己变成栅格、`overflow:hidden`，高度铺满视口：站点轴在卡内竖滚，站点卡/
  车辆列表/跟踪页都落在右栏（不再互相顶掉整页）。
- **桌面端点站 = 站点卡 + 全部车辆**：`renderStation` 末尾 `wide.matches` 那一支直接调
  `renderBusList(box, it, true)`，不用像窄屏那样再点一次「车辆列表」。`embedded` 那支省掉
  「返回站点」（桌面端没有列表页可回）和与页面标题重复的「开往 …」。
- 桌面端因此不摆卡片下那排按钮（`.cardbtns{display:none}`）：「车辆列表」已经自动出，
  「反方向站点」= 顶栏「换向」。窄屏两个都还在；窄屏开着列表时拉宽，`layoutActs` 里把
  `busListOpen` 清掉，别把列表留在右栏。
- 车徽标同样是把横排那套「段内插值」搬到竖轴：`--p` 是站间比例（1 = 正在接近的那站，
  →0 退到上一站），横排折的是 `left`、竖排折 `top` + `translateY(-50%)`，车就落在两站之间
  该在的高度上；行尾留 76px 给它，站名不与它抢位。首站上面没有上一格，退出去会被灰卡裁掉，
  所以首站钉死在站上（`.stn:first-child .bus`）。

改动全在 `index.html` 的 `@media (min-width:900px)` 块和 `app.js` 的 `wide` / `layoutActs` /
`renderRail` 里那一处 `scrollIntoView`，窄屏一行没动。

## 接口

| 路径 | 说明 |
|---|---|
| `GET /healthz` | 存活 |
| `GET /lines` | 全部线路（48 个方向 = 车来了 46 + 掌上公交 2），含后台刷出来的运营状态与车辆数 |
| `GET /lines/{lineId}` | 单条线路：站表、走向、首末班、票价 |
| `GET /lines/{lineId}/realtime?targetOrder=N` | 实时车辆；带 `targetOrder` 时 ETA 算到第 N 站，不带则算到终点 |
| `GET /` | 面板 |

上游出错时返回 502 和明确错误，**不返回空数组假装「没车」**。

## 玉林现行规则适配

面板有几处跟上游数据不完全对得上的地方。**这些都是在适配公交公司的现行运营规则，
不是界面上随意改名或把两套数据混同**，改动前请先读这一节。

### 9 路：首末站显示「火车站」而不是「玉林市第十中学」

上游站表里 9 路的首末站就是 `玉林市第三人民医院（玉林市第十中学）`（两个方向分别是
第 28 站和第 1 站），但按现行运营规则**这一站只在学生上学、放学时段停靠**，其余班次
实际以它前一站 `火车站` 为终点。

所以：

- 列表和详情页的首末站写作 **`毅德国际商贸城 - 火车站`**，这是照运营规则写的 ——
  写成「第十中学」会变成「末班车 18:55 到第十中学」，而那一班车实际停在它前一站，是错的。
- 走向条上那一格仍然是真站名 `玉林市第三人民医院（玉林市第十中学）`，方块画成空心环，
  点开卡片出说明「仅学生上学、放学时段启用」。它确实是线路的一站，不能从站表里删掉，
  否则这一站就没法查了。
- 简称只用于**显示**。走向条、找同名反向站、判断方向仍然用真站名，否则跨方向匹配会失效。
- 搜索跟着别名走：搜「火车站」也能搜到 9 路。

映射写在 `internal/panel/app.js` 的 `TERMINUS_ALIAS` 与 `STOP_NOTES`。哪天运营规则变了
（比如这一站改成全天停靠），改这两个表，不要动站表。

详情页头部还会把这件事原样说一遍（`DIR_NOTES` 里 9 路那条，两个方向都显示）：站表里
明明有个第十中学、页面上写的却是火车站，不解释一句就成了数据对不上。

### 6 路夜班、G02 路定制：与日班合并成一条展示

上游把夜班/定制当作**独立的线路**（另一套 `lineId`、另一套走向和首末班）：`6` 与
`6路夜班`、`G02` 与 `G02路定制`。

面板按线路名把它们**合并成一条**（`6`、`G02`），标签行给一个「日班 / 夜班」切换按钮。
合并只是让用户不必在两行里找同一件事：G02 与 G02 定制的起讫站完全相同，6 路夜班与日班
共用 `人民大北路口` 一端、朝向一致（站数 43 / 36 不同）。

合并**只是入口合并，数据没有混**：切到夜班时站表、首末班、票价、车辆全部换成夜班的
那一套（`setShift`），走向条也跟着换。变体方向在上游的排列顺序与日班不同（G02 定制
先列总站→北站），切换时按起终点把同一走向找回来，找不到完全同走向的就按终点兜底。

**日班收班后自动切到夜班/定制**：判据是「当前看向那一向」的日班末班时间，不用整条线
的并集 —— G02 两向末班差 70 分钟（北站→总站 19:50 / 总站→北站 18:40），早收班的那一向
本来就该先切。用户手动点过变体按钮之后就不再自动切（`shiftTouched`），免得 10 秒一次的
刷新跟人抢；换线路时重置。

### 23 路：18:50、19:15 两班只到城西开发区

上游站表只有一条全程站序，**看不出「哪几班中途折返」**。据玉林公交微信公众号，23 路
`瓜地坡 → 工业品电器城` 方向 **18:50、19:15** 从瓜地坡开出的车次到 `城西开发区`（第 19 站）
为止，不再往工业品电器城走。

面板在该方向详情页的头部（标签行下面）显示这行提醒，反向、别的线路都不显示。表在
`internal/panel/app.js` 的 `DIR_NOTES`，按「线路名 + 起终点」匹配 —— 上游的 `lineId` 会换，
名字才是我们一直在用的键。班次改了改这一条，来源一并写在旁边。

只提醒，不把第 20 站往后改样：那一天只有这两班折返，改了就成了别的班次也这样。

## 549–554：车牌 → 自编号映射（`plate_map.json`）

车来了的 `licence` 字段**类型不稳定**，同一支车队里两种写法都出现：

| 写法 | 例子 | 谁 |
|---|---|---|
| 自编号（纯数字） | `433`、`548` | 绝大多数车 |
| 车牌 | `桂K11878D` | 549–554 这 6 辆 |

549–554 是同一批车：中通 LCK6116EVGA2（2024 年，共 6 辆）。它们在车队里主要充当
**企业定制包车**，只在部分线路上做替代车。玉林市公共汽车公司工作人员表示，这批新车
计划用于旅游、商务出行、租赁以及市内大型活动用车等途径，提升乘客的乘车舒适度，为玉林
民众提供更高品质的出行服务。

这 6 辆的 `licence` 一直是车牌、没换成自编号（原因未向公交公司核实，此处不猜）。

不对齐的后果是面板上的车辆编号口径乱掉：同一支车队有的显示 `433`、有的显示
`桂K11878D`，跟公交公司口径和公开车队数据都对不上。所以用 `plate_map.json` 把这 6 对
归一，让 `Bus.FleetNo` 恒为自编号：

```json
{ "桂K12697D": "549", "桂K12593D": "550", "桂K12685D": "551",
  "桂K11878D": "552", "桂K08701D": "553", "桂K12631D": "554" }
```

`internal/plate/plate.go` 的 `FleetNo`：纯数字 = 自编号直接过；否则查表；查不到就原样
透出并打日志 `未知车牌 "X" —— 请补进 plate_map.json`，跑一轮就能收齐待补项 —— 所以
缺表不致命。归一值放 `Bus.FleetNo`，上游原值留在 `Bus.RawID`：界面只显示前者，出问题
还能对回上游。`548` 不在表里 —— 它本来就返自编号，**549 才是这批的起点**。

**这张表怎么来的**：buspedia（巴士派迪）的免登录端点 `line/photos/{lineId}` 带 `veh`
字段、形如 `"551 / 桂K 12685D"`，正好是自编号/车牌对 —— 用它交叉核验了 551、552、554；
549、550 手工录入；553 只在需登录的 `comp/fleet` 里，单独确认后补上。至此 buspedia 上
`6dyp04` 车队 6 辆齐全。（登录那条路已放弃：实测验证码真实有效期约 21 秒，服务端声称
300 秒，人工转递不可行。）

**实测证据**：仓库快照 `data/realtime.json`（46 个方向、84 个车次）里，84 个 `licence`
取值中**唯一非数字的就是 `桂K11878D`（= 552）**；数字取值区间 `365–548`，**549–554
一个都没以自编号出现过**。日常抽样（46 个方向、79 辆在线）也全是自编号 —— 这 6 辆很少
上线，跟「只做替代车」对得上。

## 第二条数据面：掌上公交（北流105路）

车来了的玉林城（`cityId=440`）只有 23 条市区线，北流、容县这些县市线路它一条都没有
（陆川只有 `605` 那条）。掌上公交（`h5.mygolbs.com`）有北流105路，双方向实时都是真的，
所以补了第二个上游客户端 `internal/mygolbs`，目前只服务这一条线。

**分派靠 lineId 前缀**：`mg` 开头走掌上公交，其余走车来了（`internal/server` 里那两处
`mygolbs.Handles(id)`）。`/lines` 把两边目录拼在一起；面板本身不区分数据面，只有底部那行
「数据更新 … · X」按 `line.src` 显示（车来了 / 掌上公交）。

`lineId` = `mg` + 掌上公交的 `routeId` + `-` + 方向（`mg40105-1` / `mg40105-2`）。
**加一条县市线路 = 在 `internal/mygolbs/mygolbs.go` 的 `catalog` 里加两行**（每方向一行），
别处不用动。

### 字段怎么对上的（都是实测，不是猜）

| 面板字段 | 掌上公交 | 说明 |
|---|---|---|
| `stops[].order` | `103` 的 `stationOrder` | 1 基，直接透出 |
| `buses[].order` | `104` 的 `list[].index + 1` | 上游 `index` 是 0 基，官方 H5 包也是拿 `index+1` 当站序 |
| `buses[].state` | `list[].statusType` | `"0"` = 已到站（官方包注释「到站的直接赋值为最近站」），其余 = 在途 |
| `buses[].pos` | 车坐标在两站之间投影 | 车与站同一坐标基准（104 的 `station_lat` 与 103 逐位相同），直接算比例 |
| `buses[].eta` | `routeOnStationRTimeInfoList[].busToStationTime` × 60 | 上游给的是分钟；点站时按 `STATIONORDER` 问该站 |
| `buses[].fleetNo`/`rawId` | `list[].busNumber` | **就是车牌**（车来了那边多是自编号），所以不过 `plate_map`、`confidence` 恒 `high` |
| `buses[].updatedAt` | `list[]._recTime` | 毫秒，是上游自己的记录时间，不是本地 `now` |
| `price` | `commonts` 里的「票价：X」 | 全线路只有这一处写着票价 |
| `state` / `desc` | `runState` / `hasReal` | `runState=1` → 停运；`hasReal=0` → 未开通实时查询 |

`Origin: https://h5.mygolbs.com` 是这个接口的硬门槛：少了它**所有命令**都返回同一个 47 字节
网关串（HTTP 200、不是 JSON），看着像「上游挂了」。另外 `CMD=101` 的城市列表**不能**用来判覆盖
—— 陆川的线路挂在玉林市 `450900` 下面就说明了这点，别拿它当目录。更细的实测记录见
`docs/掌上公交API立项报告.md`。

### 已知边界

- **每站只给最近 2 辆车的预测**（上游 `routeOnStationRTimeInfoList` 最多两条），第 3 辆起没有 ETA。
  面板显示「无预测」，不猜「即将到站」—— 这也是 `app.js` 里那处文案改掉的原因。
- **班表（`207`/`116`）没接**：面板还没有班表位。
- 站表缓存 1 小时、目录（含车辆数）1 分钟；实时不缓存 —— 面板 10 秒刷一次，点站还会单独问一次。
- 抓包存在 `internal/mygolbs/testdata/`（2026-10-12 08:30 CST 的真实响应），单测按它断字段映射。
